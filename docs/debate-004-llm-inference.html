Debate 004

What is vLLM, the KV cache, and attention?

Three topics that are really one chain: the operation, the thing it forces, and the system built to feed it.

Status: Open Draft 0.1 Opened 23 Oct 2026 Editor Divyansh Tripathi Draft · Not settled

00Framing: one machine, three objects

Asked separately, these three look like three topics. They are one chain. Attention is the operation — a learned retrieval. The KV cache is what autoregressive generation forces attention to keep. vLLM is the system that manages that cache so the machine can actually be fed.

Each one creates the next
  1. The operation creates the cache.
  2. The cache becomes the bottleneck.
  3. The bottleneck demands a system.

01Attention, minimally

For each token, a self-attention layer projects its hidden state into three vectors: a query q = W_q·x, a key k = W_k·x, and a value v = W_v·x. Then, for each query, it compares against every key and takes a weighted average of the values:

aij = softmax( qi · kj / √d )
oi = Σj aij · vj

That is the whole operation. Read plainly, it is a retrieval: the query is a search term, the keys are an index, and the output is a soft, weighted lookup into the values. Every token asks "which earlier tokens are relevant to me?" and pulls a blend of them.

  • Compute is quadratic in sequence length — the score matrix is N × N.
  • Two phases, opposite bottlenecks. Prefill (the prompt) knows all tokens at once → matrix–matrix → compute-bound. Decode (generation) works one token at a time → matrix–vector → memory-bound.

That asymmetry is the hinge of the whole chapter.

Tangent

Attention was invented for translation. Bahdanau et al. introduced it in 2014 to let a decoder look back at the encoder's words — and the 2017 paper that removed the recurrence entirely was titled, with some swagger, Attention Is All You Need.

02Why the cache exists

Language models generate autoregressively: token t depends on all tokens before it. To produce token t+1, the model must attend over the keys and values of tokens 1 … t. Without a cache, every step would recompute the keys and values of the entire prefix — the same vectors, over and over. Across a generation of n tokens that is O(n²) redundant work. The KV cache fixes it: store the key and value vectors as they are produced, so each step computes only the new token's k and v and attends over the cached ones.

  • The cache changes nothing about the output. It is memoization, not approximation — generation with and without it produces identical tokens. It buys speed, never accuracy.
  • It moves the cost from compute to memory. Each decode step becomes O(n) in attention (it must read the whole cache) and O(1) in weight matrix products. The redundant compute is gone; what remains is a large, growing tensor read on every step.
Tangent

The KV cache changes nothing. Greedy generation with and without it produces bit-identical tokens. It is pure memoisation — the same answer, computed less wastefully.

03The size — and why it is the bottleneck

The cache's size is simple to write down. For a model with L layers, h key/value heads, head dimension dh, context length S, in 16-bit:

KV bytes = 2 (keys and values) × 2 (bytes) × L × h × dh × S = 4 · L · h · dh · S

It grows linearly in context length and batch size — and it is not a rounding error. For LLaMA-3-70B (L=80, h=64, dh=128):

Context lengthKV cache (MHA)With GQA (8 KV heads)
4,096 tokens≈ 10.7 GB≈ 1.3 GB
32,768 tokens≈ 85.9 GB≈ 10.7 GB

At 32k context the MHA cache alone exceeds the 80 GB of an H100. One analysis puts an 8B model at batch 128 and 8,192 tokens at 280 GB of MHA cache — about 30× the model's own weights (69 GB with GQA).

Now put that against the roofline. A kernel's arithmetic intensity — FLOPs per byte moved — decides whether it is compute- or memory-bound. On an H100 the ridge point is about 295 FLOP/byte. Prefill sits well above it. Decode, at small batch, sits at roughly 1 FLOP/byte — two to three orders of magnitude below the ridge. The tensor cores idle; measured GPU utilisation during decode can fall to around 7%.

The cache is not "large in the abstract." Decoding must re-read it every step while doing almost no math — so the cache's size, not the model's, becomes the binding constraint.

Tangent

For a 70B model at 32k context, the KV cache alone is about 85.9 GB — larger than the entire 80 GB memory of an H100. The cache is bigger than the machine that has to hold it.

04vLLM: the system that manages it

vLLM is not a model, an architecture, or a training method. It is an inference engine — a serving system. Nothing about it changes what the model computes; it changes how fast and how cheaply the model can be run.

The problem. Serving is memory-bound, and the memory is dominated by the KV cache. To keep a request's cache contiguous, prior systems pre-allocated a chunk sized to the request's maximum length. Three kinds of waste followed — slots reserved for future tokens, internal fragmentation, and external fragmentation. The measured result: in prior systems only 20.4%–38.2% of KV-cache memory was actually used to store real token states.

The trick — PagedAttention. Borrow OS virtual-memory paging: split a request's cache into fixed-size blocks; let the blocks be non-contiguous in physical memory; and keep a per-request block table mapping logical blocks to physical ones — pages, tokens as bytes, requests as processes.

  • Near-zero waste. On-demand, uniform-size blocks kill external fragmentation and confine internal waste to the last, partly-filled block — in practice under 4%, against the 60–80% of the naive scheme.
  • Sharing becomes possible. Sequences sharing a prefix can point at the same physical blocks. Parallel sampling saved 6–10% of memory; beam search, 38–55%, and up to 66% on real chat data.

On top sits continuous batching (iteration-level scheduling): finished requests are dropped and new ones admitted every decoding iteration — no padding, no head-of-line blocking.

 Naive contiguous cachePagedAttention
KV-cache utilisation20.4–38.2%>96% (waste <4%)
Cross-request sharingnoneblock-level
Throughput vs. baseline1×2–4× (up to 22× vs. FT)

Model outputs are bit-for-bit unchanged. This is pure systems work.

Tangent

PagedAttention is not a new idea so much as a borrowed one. It is operating-system virtual memory, transplanted: pages become blocks, bytes become tokens, processes become requests. The trick is roughly sixty years old — it had simply never been applied to a KV cache.

05The debates

D1 — Architecture: share the heads. Make fewer keys and values to begin with. MHA (standard) has one key/value head per query head. MQA (Shazeer, 2019) uses a single shared key/value head — the cache shrinks by a factor of h, but quality suffers and the single head must be replicated across devices. GQA (Ainslie et al., 2023) groups queries, each group sharing one key/value head — recovering most of the quality; now the default in Llama 2 70B / Llama 3, Mistral, Qwen. MLA (DeepSeek) caches a low-rank latent instead. The trade-off is explicit: quality vs. KV budget vs. parallelizability.

D2 — Management: page it. PagedAttention does not shrink the cache; it stops wasting it. But is paging necessary? vAttention (2024) argues you can manage the cache dynamically with CUDA's own virtual-memory APIs, without a custom block abstraction.

D3 — Precision: quantize it. FP8 or INT4 halves or quarters the bytes, and FP8 gives a near-2× decode win. But PyTorch found an INT4 GQA cache read 4× less data for no latency improvement at all, because the kernel was less bandwidth-efficient. Fewer bytes ≠ faster.

D4 — Algorithm: don't materialize it. A widespread confusion: FlashAttention does not reduce the KV cache. It is exact attention that avoids writing the N × N score matrix to slow HBM, by tiling into on-chip SRAM. On a GPT-2 attention block, HBM traffic fell 40.3 GB → 4.4 GB and runtime 41.7 ms → 7.3 ms. The cache itself is unchanged.

D5 — Approximation: the road not taken. Sparse and low-rank attention reduce FLOPs to near-linear, yet many "do not display wall-clock speedup against standard attention, and have not gained wide adoption" — because they optimised FLOPs and ignored memory I/O. FLOPs are not time; bytes moved are.

D6 — The landscape. vLLM is one engine among several: TensorRT-LLM (NVIDIA; often fastest raw latency), TGI (Hugging Face), SGLang (RadixAttention — prefix reuse, a different axis), LMDeploy. No universal winner; the trade-offs are workload-dependent.

D7 — Is this research? The vLLM paper appeared at SOSP, an operating-systems venue — not an ML conference. As architecture matures, the bottleneck moves to systems, and the most impactful work stops looking like ML.

A systems-level trend sits above all of these: prefill/decode disaggregation — running the compute-bound prefill and the memory-bound decode on different hardware, since they stress opposite resources.

Tangent

GQA was designed to be retrofitted. You take an existing multi-head model, mean-pool its key and value heads into groups, and continue training for just 5% of the original compute. Most of the world's fast models were converted, not retrained.

06What the evidence, read together, suggests

  1. The three objects are one chain. Attention forces the cache; the cache is the bottleneck; vLLM is one answer to it.
  2. The cache is exact. It never changes the output — only the speed — and it moves cost from compute to memory.
  3. Decode is memory-bandwidth-bound, and arithmetic intensity is why. This is why batching is the primary lever and why the cache is worth shrinking.
  4. The fixes live on different axes — architecture, management, precision, algorithm — and they compose. GQA + PagedAttention + FP8 + FlashAttention is a coherent stack, not four rival ideas.
  5. FLOPs are not wall-clock. The approximate-attention story and the INT4 story are the same cautionary tale from opposite directions.
  6. vLLM is a memory manager and a scheduler, not a model. Keeping that boundary clear is most of the answer to "what is vLLM."
