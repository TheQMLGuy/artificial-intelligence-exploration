Debate 004

What is vLLM?

Not a model. Not an architecture. A memory manager wearing an inference engine's clothes.

Status: Open Draft 0.1 Opened 23 Oct 2026 Editor Divyansh Tripathi Draft · Not settled

00Framing: vLLM is not a model

The name invites the wrong picture. vLLM is not an architecture, not a model, and not a training method. It is an inference engine — a serving system. Nothing about it changes what the model computes; it changes how fast and how cheaply the model can be run.

Three questions, stacked
  1. What problem does it solve? Serving an LLM is a memory problem, not a compute problem — and memory is wasted badly by naive implementations.
  2. What is the trick? One idea — paging the KV cache — plus a scheduling change the paging makes possible.
  3. How well, against what? A 2–4× throughput win over the previous state of the art, in a crowded field of serving engines.

Read this alongside Debate 005 (the KV cache): vLLM's central trick is a KV-cache technique, so this chapter is the systems answer to a problem that chapter sets up.

01The problem: serving an LLM is a memory problem

Autoregressive generation produces one token at a time. Each new token depends on all previous ones, so the work is sequential — and at each step the model does a tiny amount of math (a matrix–vector product) while moving an enormous amount of data. The GPUs are not compute-starved; they are memory-bandwidth-starved.

The standard fix is batching: run many requests together so the cost of loading the weights is shared. But how many requests fit? That is decided by memory — and the memory is dominated by the KV cache, the stored keys and values of every token generated so far.

The numbers make it concrete. Serving a 13B-parameter model on an A100 with 40 GB, roughly 65% of memory holds the weights (static) and over 30% holds the KV cache (dynamic, per request). For OPT-13B the cache of a single token is about 800 KB — and at 2048 tokens one request's cache reaches 1.6 GB. Only a few tens of requests fit even if every spare byte went to cache.

And naive implementations waste most of it. To keep a request's cache contiguous, prior systems pre-allocate a chunk sized to the request's maximum length. Three kinds of waste follow — slots reserved for future tokens, internal fragmentation (the request finished long before its maximum), and external fragmentation from the allocator. The vLLM paper measured it: in prior systems only 20.4%–38.2% of KV-cache memory was actually used to store real token states.

The trend makes it worse, not better: from A100 to H100, compute throughput more than doubled while memory capacity stayed at 80 GB. Memory is the bottleneck, and it is tightening.

02The trick: PagedAttention

The insight is an old one from operating systems. Programs want contiguous memory; physical memory is fragmented. The OS solved this with virtual memory and paging — fixed-size pages, mapped from logical to physical through a page table.

PagedAttention applies exactly that to the KV cache:

  • Block it. A request's KV cache is split into fixed-size blocks, each holding the keys and values for a fixed number of tokens.
  • Scatter it. The blocks need not be contiguous in physical memory.
  • Map it. A per-request block table maps logical blocks to physical ones — pages, tokens as bytes, requests as processes.

The consequences are the whole point:

  • Near-zero waste. Blocks are allocated on demand and all have the same size, so external fragmentation disappears and internal waste is confined to the last, partly-filled block — in practice under 4% waste, against the 60–80% of the naive scheme.
  • Sharing becomes possible. Because sharing is at block granularity, sequences that share a prefix can point at the same physical blocks. Parallel sampling saved 6–10% of memory; beam search, 38–55%, and up to 66% on real chat data.

On top of the paging sits continuous batching (iteration-level scheduling): instead of admitting a fixed batch and waiting for the longest sequence, the scheduler drops finished requests and admits new ones every decoding iteration — no padding, no head-of-line blocking.

03The debates

D1. Memory or batching — which is the real lever? Both, but not symmetrically. The throughput win comes from batching more requests, and batching more requests is only possible because paging freed the memory. The causal chain is paging → memory → batch size → throughput. Calling it "a batching trick" undersells the memory work; calling it "a memory trick" hides why memory matters.

D2. PagedAttention, or just manage the cache better? A follow-up system (vAttention, 2024) argues paging is not necessary — you can manage the cache dynamically with CUDA's own virtual-memory APIs, without a custom block abstraction. If that holds, PagedAttention's win is less "a new algorithm" than "the right fix for a limitation the existing allocators had."

D3. vLLM vs the field. The landscape is crowded: TensorRT-LLM (NVIDIA; often the fastest raw latency, less flexible), TGI (Hugging Face), SGLang (whose RadixAttention attacks prefix reuse, a different axis), and LMDeploy. There is no universal winner — throughput, latency, hardware and features trade off per workload. "vLLM is fastest" is a workload-dependent claim, and should be quoted as one.

D4. Is this research? The paper appeared at SOSP, an operating-systems venue — not an ML conference. That is the debate in miniature: as architecture matures, the bottleneck moves to systems, and the most impactful work stops looking like ML.

D5. What vLLM is not. It does not make the model smarter, change its output, reduce its weights, or alter its math. It is a scheduler and a memory manager. Keeping that boundary clear is most of the answer to "what is vLLM."

04What the evidence, read together, suggests

This is a reading, not a verdict. The editor decides what stands.

  1. vLLM is an inference engine, not a model. Its entire contribution is systems: memory management and scheduling.
  2. The problem it solves is memory-bound serving — specifically the waste and inflexibility of KV-cache allocation.
  3. PagedAttention is the core idea: block the cache, map it through a table, share at block granularity — near-zero waste and real memory sharing.
  4. The measured win is 2–4× throughput over the prior state of the art, larger for long sequences and complex decoding, with unchanged outputs.
  5. The claim is contested at the edges — a follow-up questions whether paging is necessary at all, and the competitive landscape is workload-dependent.
